# Taily Database Migrations & Schema Management

## 1. Core Principles

1. **Deterministic Version Control**: All production schema changes MUST be managed through versioned SQL migration files generated by Prisma (`prisma/migrations/*`).
2. **NO Destructive Automatic Push**: `npx prisma db push` is strictly prohibited in staging and production environments. It lacks change history, cannot be rolled back, and risks accidental column/table drops.
3. **Pre-Migration Backup Mandatory**: Never execute a database migration in production without a verified point-in-time database snapshot.
4. **Backward Compatibility (Expand-and-Contract)**: Migrations must not drop or rename columns in a single step if active application instances still rely on them.

---

## 2. Standard Migration Lifecycle

### Step 1: Development Schema Changes
Make edits to `prisma/schema.prisma`. Then generate a named migration locally:
```bash
npx prisma migrate dev --name add_composite_indexes_for_tenant_speed
```
Prisma will:
1. Generate the SQL migration in `prisma/migrations/<timestamp>_<name>/migration.sql`.
2. Apply the migration to your local development database.
3. Regenerate Prisma Client.

### Step 2: Code Review & SQL Inspection
Review the generated SQL file:
- Verify that table alter statements do not contain unwanted `DROP TABLE` or `DROP COLUMN` commands.
- Ensure that compound indexes match high-frequency access paths (`companyId + sku`, `companyId + date`).
- Verify foreign key cascades (`onDelete: Cascade` vs `onDelete: Restrict`).

### Step 3: Production Execution
In your CI/CD pipeline or deployment hook:
```bash
# 1. Create pre-migration safety backup
node scripts/backup-pre-migration.js

# 2. Apply pending migrations
npx prisma migrate deploy

# 3. Verify status
npx prisma migrate status
```

## 3. Database Indexes Architecture

Taily utilizes strategic composite and single-column B-tree indexes to guarantee sub-30ms query latency under enterprise scale (10,000+ invoices and items):

| Model | Index Specification | Primary Use Case |
|---|---|---|
| `Item` | `@@index([companyId, sku])` | SKU lookup and POS barcode scanner search |
| `Item` | `@@index([companyId, barcode])` | Instant handheld barcode scan item resolution |
| `Item` | `@@index([companyId, active])` | Filter active inventory in dropdowns and pickers |
| `Party` | `@@index([companyId, type])` | Filter Customers vs Vendors |
| `Party` | `@@index([companyId, name])` | Autocomplete and party search |
| `Invoice` | `@@index([companyId, date])` | Date range filtering for Day Book, P&L, and GST |
| `Invoice` | `@@index([companyId, partyId])` | Subledger outstanding balance and statement queries |
| `Invoice` | `@@index([companyId, warehouseId])` | Warehouse-specific sales and delivery challans |
| `Invoice` | `@@index([companyId, type, status])`| Dashboard KPI aggregations and overdue tracker |
| `StockMovement` | `@@index([companyId, warehouseId, date])`| Inventory ledger and stock valuation reports |
| `StockMovement` | `@@index([companyId, movementType])`| Movement audit trail and transaction type grouping |
| `WarehouseStock` | `@@index([companyId, itemId])` | Instant stock check during invoice creation |
| `Voucher` | `@@index([companyId, date])` | General Ledger and Day Book range scans |
| `VoucherEntry` | `@@index([accountId])` | Trial Balance and account summary aggregations |

## 4. Rollback & Recovery Strategy

If a migration fails or causes unexpected production locks:

### Step 1: Halt Application Traffic
Temporarily display a maintenance page to prevent incoming write traffic.

### Step 2: Restore Pre-Migration Snapshot
```bash
# Restore from the automated snapshot created prior to migration
node -e "require('./src/lib/backup').restoreDatabaseBackup('./backups/pre-migration-snapshot.db')"
```

### Step 3: Mark Migration as Rolled Back in Prisma
If Prisma's `_prisma_migrations` table recorded a failed state:
```bash
npx prisma migrate resolve --rolled-back <migration_name>
```

## 5. Migration Safety Checklist

- [ ] Does the migration add columns as nullable or with sensible `@default(...)` values?
- [ ] Are all new tables indexed with `companyId` for multi-tenant query acceleration?
- [ ] Is foreign key deletion behavior explicitly declared (`Cascade`, `SetNull`, or `Restrict`)?
- [ ] Has the migration been tested with realistic volume in a staging environment?
- [ ] Is the backup verified before executing `prisma migrate deploy`?
